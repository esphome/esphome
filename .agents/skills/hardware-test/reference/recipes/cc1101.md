# cc1101

## Sleep and wake checks read from the chip (#22519)

`scripts/cc1101_sleep/`: `cc1101-sleep.yaml` runs an ESP32-S3 (ESP-IDF) with an E07-M1101D module on SPI and runs
tests T0 to T6 4 s after boot; `cctest.hpp` reads every config register and the PATABLE directly over SPI. The log
ends with `DONE fails=N`, and T6 prints whether each setter woke a sleeping chip.

- Proof that the chip sleeps: with CSn low, SO (MISO) stays high until the crystal runs, so it is high after
  `power_down()` and low at once when awake. PATABLE entries 1 to 7 are also lost in SLEEP, so write marks to them
  before `power_down()` and check that they are gone.
- Selecting the chip to check it wakes it, so after the check the chip is awake while the component still thinks it
  sleeps. Call `wake_up()` and `begin_rx()` before the next case.
- Leave FSCAL3 to FSCAL1 (0x23 to 0x25), FSTEST (0x29) and AGCTEST (0x2B) out of register comparisons: calibration
  and the chip itself change them.
- Results: on 7e6b90d08b, `set_frequency`, `set_channel` and `set_modulation_type` woke a sleeping chip and left it
  in RX. 9e65d0c327 fixed that; every other check passed on both, and 200 sleep and wake cycles took about 1 s.

## Long packets and lambda length, two radios (#17578)

`scripts/cc1101_long/`: `cccommon.yaml` (package, API actions `cfg`, `send`, `rate`, `pdown`, `wup`, `setlen`,
`pmode`, `idle_rx`, `tx_rx`, `hf` and more; logs every packet as `RX len= b0= seq= ok= rssi= lqi= fo=`), `cclong.hpp`
(raw register helpers and `long_tx()`, which streams packets longer than the TX FIFO per datasheet 15.2.2, since the
component only sends up to 64 bytes), example board files `c3-long.yaml` / `s3-long.yaml` / `c3-lambda.yaml` (plen 32 =
plain, 1024 = long, lambda `x[0] + 1` with 0xEE meaning -1), `ccdrive.py TXHOST RXHOST MODE OUT TXLABEL RXLABEL`
(modes `short`, `long`, `r2long`, `r2mid`, `lambda`, `r2lambda`, `fast`, plus the dev bug repros `crc`, `rxtx`,
`txback`, `txrx` and `txset` (begin_tx then begin_rx, with setters between them, #22636) and `nocrc64` (100 packets of
64 bytes with and without CRC, #22635)), `flashmac.sh NAME BOARD` (BOARD is a port or the USB serial number from
`ports.py`; flashes, then waits for the API with `ota_timing/apiinfo.py`), `buildall.sh NAME...`, `runall.sh A B`
(both roles, boards as for flashmac.sh). Needs `secrets.yaml` with `api_key` and an `apikey.txt` file with the same key next
to the configs.

- Two boards with an E07-M1101D each, 433.92 MHz GFSK 4800. Ports change after a replug; flash by USB serial number.
- Both radios on the PR: one plain, one long and one lambda build per board; the sender runs the long build (raw TX
  does not care). A full both-roles run is about 45 min including builds.
- Order matters: `tx_rx` (begin_tx then begin_rx) kills reception until reflash or `set_packet_mode(true)` on dev
  (#22636), so run `long` last on a build and keep it out of `lambda`; `r2lambda` sets a fixed length, which drops
  the lambda, so run it after `lambda`. Fixed 64 with CRC is 0/20 on dev too (#22635).
- `ccdrive.py` waits for the RX and TX `CFG` log line before sending; without that a slow API reply leaves the
  receiver on the previous length and shows "wrong length" packets.
  A result line is marked INVALID when an action failed or a `CFG`, `RATE` or `SENT` line never came since the
  previous result, and shows the sender's `txerr` from its `SENT` line, so send failures are not read as lost packets.
  A case is MISSED, and ccdrive.py exits non-zero, when the sender reports send errors (or no SENT line), when fewer
  than 80 % of its packets arrive good, or when any arrives for the cases that expect none (asleep, lambda discard);
  the dev bug repros, 64 bytes with CRC (#22635) and the receiver after begin_tx plus begin_rx (#22636) are reported
  but not judged.
- High rate (`fast`): the `rate` action sets modulation, symbol rate, deviation, filter and sync at run time on both
  radios, and `long_tx` polls at 20 to 50 us. Use sync 30/32: with 16/16 at 100 kBaud noise syncs about once a second
  and collides with real packets. At 100 kBaud a stable RXBYTES read alone overflowed at the first drain
  (`received=0 expected=300 fifo=65`, 10/20 at 300 B on the C3) and the GDO0 drain got 20/20; 38.4k showed no
  difference. The C3 shows the overflow more than the S3.
- A strong RSSI (about -29 dBm) with ok=0 is a real corruption; ok=0 at -90 dBm, LQI 127 is a noise sync.
- An API drop mid-run can be a Wi-Fi roam scan, not a restart (check serial); rerun.

## begin_tx in packet mode, async serial OOK with remote_transmitter/receiver (#22636)

Same two boards and `scripts/cc1101_long/` tools. `cccommon.yaml` has two more actions: `btx` logs PKTCTRL0 before
and after `begin_tx()` plus MARCSTATE, and `swasync` switches to async serial, runs `begin_tx()`/`begin_rx()` and
switches back. `ookcommon.yaml` is async serial ASK/OOK with remote_transmitter and remote_receiver (actions `send`,
`pdsend`, `pdtx`, `pdown`, `regchk`, `state`); `c3-ook.yaml` and `s3-ook.yaml` are example board files.
`ookdrive.py PEER DUT OUT [ROUNDS|probe]` sends NEC codes both ways and runs the sleep and register checks on DUT;
`probe` sends 3 codes each way for setting up. Flash with `flashmac.sh` as above and run the drivers with
`API_KEY=$(cat apikey.txt)`.

- Packet mode check: `ccdrive.py PEER DUT btx OUT`. Before #22636, `begin_tx()` set PKTCTRL0 to 0x32 (async serial),
  then 0/20 packets arrived and `send_packet` was refused (`packet mode is not FIFO`) until the mode was set again.
  With it, `begin_tx()` only logs a warning and 20/20 and 10/10 pass. Do not call `cfg` between `btx` and the counts
  (`rx_len=-1`): `cfg` runs `begin_rx()` and hides the bug.
- OOK wiring: GDO0 is the only data pin. Use the single-pin open-drain example from the cc1101 docs: remote_receiver
  and remote_transmitter on the GDO0 GPIO, both `input`/`output`/`pullup`/`open_drain` with `allow_other_uses`, no
  `gdo0_pin` on `cc1101:`, `eot_level: false`, `carrier_duty_percent: 100%`. `on_transmit`: `cc1101.set_idle`,
  `remote_transmitter.digital_write: false`, `cc1101.begin_tx`. `on_complete`: `cc1101.set_idle`,
  `remote_transmitter.digital_write: true`, `cc1101.begin_rx`. Each board also decodes its own sends through the
  shared pin, so count codes by command range per direction.
- Receiver settings that make NEC decode: `idle: 12ms` (with 6 ms the 9 ms NEC leader counts as idle and raw dumps
  start at -4500, so nothing decodes), `filter: 250us`, `rmt_symbols: 96` on the C3 (192 on the S3). With these,
  19/20 or 20/20 each way.
- begin_tx on a sleeping chip: the documented `on_transmit` calls `set_idle` first, which wakes the chip, so it does
  not test this. `pdsend` sets a global flag that skips `set_idle` and calls `power_down()` before one code; `pdtx`
  runs `power_down()`, then `begin_tx()`, then reads MARCSTATE (0x13 = TX). The register read itself wakes the chip,
  so read only after `begin_tx()`.
- PKTCTRL0 marker: in async serial mode the default PKTCTRL0 is 0x32, the same value the old `begin_tx()` wrote, so
  a readback cannot show whether it writes. `regchk` sets the CRC bit (`set_crc_enable(true)`, 0x36; async serial
  ignores it), calls `begin_tx()` and reads it back: the old code gives 0x32, #22636 keeps 0x36. Then it clears the
  bit.
