# RGB888 output and automatic static images

LVGL accepts `color_depth: 16` (the unchanged default) or `color_depth: 24`.
24 means packed RGB888: three bytes per output pixel. Transparent images and
blending layers can still use ARGB8888 independently of the display format.
All LVGL instances in one firmware must use the same colour depth.

## Supported displays

24-bit output requires a driver that declares a 24-bit path through both its
framebuffer and panel interface. A driver that accepts RGB888 input but reduces
it to RGB565 is not sufficient. Unknown external drivers keep working with the
16-bit default; they must declare their capability before enabling 24-bit LVGL.

Currently declared paths:

- MIPI DSI with both `color_depth: 24` and `pixel_mode: 24bit`.
- Host snapshot display with `color_depth: 24`, including its backing buffer.

Use little-endian LVGL byte order for RGB888 (B, G, R bytes in memory). This is
independent of a panel's RGB/BGR setting. Existing RGB565 byte-order settings
continue to work as before.

```yaml
# Add these settings to an otherwise complete MIPI DSI display configuration.
display:
  - platform: mipi_dsi
    id: main_display
    # model, pins, dimensions and panel timings are board specific
    color_depth: 24
    pixel_mode: 24bit
    auto_clear_enabled: false
    update_interval: never

lvgl:
  displays: main_display
  color_depth: 24
```

The framebuffer is 50% larger: 800x800 changes from 1,280,000 to 1,920,000 bytes.
Display traffic also increases. Panel timings that work with RGB565 may not be
stable with RGB888; verify the pixel clock, PSRAM bandwidth and panel timing
requirements on the hardware. A successful build does not establish visual
stability. RGB888 does not promise a higher frame rate.

## Encode static images for the selected output during the build

```yaml
image:
  - platform: file
    id: room
    file: room.png
    type: AUTO
    target_display: main_display
    transparency: alpha_channel
```

`AUTO` selects the embedded format on the build computer. Keep the original
full-colour source; no preprocessing is necessary. A target driven by 16-bit
LVGL selects RGB565, and a target driven by 24-bit LVGL selects RGB. Without LVGL,
the target's declared native depth is used. Alpha is retained when requested.
Changing the depth and rebuilding regenerates the embedded bytes.

`target_display` may be omitted if exactly one display is configured. With
multiple displays it is required. It selects the image's encoding, not where
C++ code is allowed to draw the image. To use the same source in two embedded
formats, define two image IDs with different targets. The firmware stores only
the explicitly requested assets; there is no hidden duplicate full-colour copy.

`type: RGB` continues to mean an explicitly full-colour embedded image; it is not
silently reduced to RGB565. Existing RGB565, grayscale and binary types keep
their meaning. Use AUTO when the format should follow the target. Do not specify
`target_display` with an explicit type. Format-incompatible byte-order options
produce configuration errors.

File-backed animation supports the same AUTO/target options. Each frame is
encoded in the resolved format, including its alpha data. Defaults/files groups
and existing legacy image and animation syntax are supported.

This conversion applies to files available at build time, including downloaded
build-time assets and rasterised SVGs. `online_image` and other runtime sources
must select an explicit supported type: their content is unavailable during the
build. Transparent images still require blending on the device against the
current background. AUTO eliminates format conversion of matching opaque static
assets, not all rendering work.

## Driver authors

Extend the existing `display.add_metadata()` call with
`native_color_depth=16` or `24`, derived from the resolved configuration. Leave
it unset when unknown. The declaration describes preserved colour precision,
not just an input format accepted by `draw_pixels_at()`. Do not declare 24 if any
framebuffer or panel stage truncates channels to RGB565.

At 24 bits, verify byte layout, three-byte strides, source offsets, row padding,
partial rectangles, clipping and rotation. A red ramp with 256 distinct values
must retain those values. Exporting an RGB565 buffer into a 24-bit BMP does not
pass this test.

## Validation

`tests/integration/test_lvgl_rgb888.py` checks actual rendered pixels in a native
24-bit host buffer, AUTO assets, alpha, animation, all four rotations, odd screen
sizes and partial redraws. Python tests check configuration errors, target
inference, YAML ordering and exact encoded bytes. The existing RGB565 reference
render remains a regression test.

Hardware validation must separately record the board, SDK, clocks and visual
results. Driver capability is not a guarantee that arbitrary panel timings are
safe.
